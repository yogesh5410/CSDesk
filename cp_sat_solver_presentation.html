Theoretical Foundation

What is Google OR-Tools CP-SAT?

CP-SAT merges two powerful computer science disciplines: Constraint Programming (CP) and Boolean Satisfiability (SAT) solvers.

🧩

Constraint Programming (CP)

Expresses problems declaratively through variables, finite integer domains, and arbitrary relational constraints (e.g. AddAtMostOne, table constraints, piecewise linear rewards).

⚡

SAT & CDCL Solvers

Uses Conflict-Driven Clause Learning (CDCL) from modern Boolean SAT engines to rapidly prune non-viable solution trees and learn general conflict reasons.

🎯

Lazy Clause Generation

The secret sauce: integer constraints are translated dynamically into Boolean clauses only when needed during search, combining integer bounds propagation with SAT speed.

Key Difference: Unlike Machine Learning (heuristic/statistical approximation), CP-SAT performs exact combinatorial search that guarantees a mathematical proof of optimality.
Paradigms

CP-SAT vs. Greedy vs. Linear Programming (LP)

Why traditional greedy loops and pure Linear Programming fail for complex academic scheduling.

Paradigm How It Works Major Limitation for TA Allocation
Greedy / Iterative Loop Sorts requests by priority and assigns first available TA one-by-one. Myopic: Commits to early choices without foresight. Fails when two professors clash or when proportional sharing is needed.
Mixed Integer Linear (MILP) Optimizes linear objective subject to linear inequalities via simplex/branch-and-bound. Linear bounds are weak on discrete logic (e.g., disjoint timetable intervals, complex non-linear proportional step functions).
CP-SAT (Our Choice) Maintains finite domains, enforces discrete logical implications, and searches globally. Global Optimum: Weighs all 2,000+ assignment decisions simultaneously with guaranteed clash-free feasibility.
Script Architecture

Execution Lifecycle of ta_solver.py

A 7-stage sequential pipeline transforming raw institute data into verified assignments.

Stage 1 & 2

Slot Indexing

build_slot_index() maps timetable grid cells. resolve_slots() computes exact (day, time) footprint for all courses.

Stage 3 & 4

Domain Pruning

Computes busy[roll] from student registrations. Prunes domain into eligible[code] before model creation.

Stage 5

Model & Rules

Creates Boolean decision variables $x_{t, c}$, adds hard constraints (workload $\le 1$), and builds multi-tier rewards.

Stage 6 & 7

Solve & Emit

Runs 8-worker parallel search, reports incremental improvements via callback, and returns structured JSON.

Performance Optimization

Pre-Filtering: The Eligibility Map

Crucial design principle: Never add impossible variables to the solver. Filter candidates before model creation.

Computing Busy Slots

for roll, ta in tas.items(): if ta.get("program").startswith("P"): busy[roll] = set() # PhD scholars: free in every slot else: cells = set() for code in registered.get(roll, []): cells |= course_cells.get(code, set()) busy[roll] = cells # Union of student class times

PhD scholars have 0 coursework slots. M.Tech students accumulate the exact intervals of their enrolled courses.

Pruning Infeasible Pairs

eligible = defaultdict(list) for req in requirements: code = req["course_code"] cells = course_cells.get(code, set()) for roll in tas: if not (busy[roll] & cells): eligible[code].append(roll) # ZERO CLASH

If student class hours overlap with course hours by even 1 slot, that candidate is omitted. Reduces decision variables by ~50%.

Mathematical Formulation

Decision Variables in CP-SAT

The solver instantiates two sets of Boolean decision variables inside cp_model.CpModel().

Primary Assignment Variables: $x_{t, c}$

x[roll, code] = model.NewBoolVar(f"x_{roll}_{code}")

A binary indicator variable defined only for candidate pairs where TA $t$ is strictly eligible for Course $c$:

x_{t, c} = \begin{cases} 1 & \text{if TA } t \text{ is assigned to Course } c \\ 0 & \text{otherwise} \end{cases}

Auxiliary Step Variables: $y_{c, k}$ & $\text{has}_c$

has_any = model.NewBoolVar(f"has_{code}") y = model.NewBoolVar(f"y_{code}_{k}")

Auxiliary variables that track coverage status:

  • $\text{has}_c = 1 \iff \sum_t x_{t,c} \ge 1$ (course coverage).
  • $y_{c, k} = 1 \iff$ the $k$-th seat of course $c$ is fulfilled.
Hard Constraints

Hard Constraints Enforced in ta_solver.py

Guarantees that no illegal schedule can ever be returned as a solution.

1. Workload Cap

model.Add( sum(v for _c, v in mine) <= max_per_ta )

Each TA can take at most max_per_ta courses (default $1$). Prevents student burnout and ensures load distribution.

2. Demand Ceiling

total = sum(assigned) model.Add(total <= need)

No course is ever assigned more TAs than requested by the faculty, preventing over-allocation.

3. Multi-Course Clash Guard

if max_per_ta > 1: model.AddAtMostOne([mine[i][1], mine[j][1]])

If a TA ever serves $N > 1$ courses, the solver uses AddAtMostOne to guarantee the assigned courses do not overlap in time.

Optimization

The Multi-Tier Objective Hierarchy

Integer weights are carefully scaled in decade magnitude tiers so higher-priority department policies always prevail.

Constant Value Role in Objective Function
W_HAS_ANY 100,000 Rule 1 Coverage: Guarantees every course gets at least 1 TA before any course gets a 2nd TA.
W_PROPORTIONAL 10,000 Proportional Scaling: Diminishing reward scaled inversely by total demand.
W_SEAT 1,000 Headcount Fulfillment: Flat incentive for every additional TA seat filled.
W_SUPERVISOR 200 Rule 3 Tie-Break: Sized higher than maximum preference rank so thesis guide always wins a contest.
W_PREF_TOP 100 Faculty Preference: Rank 1 gets +100 bonus, decreasing by W_PREF_STEP (5) per rank down to min 10.
Fairness Mathematics

Proportional Demand Fulfillment Formulation

How do you satisfy Rule 4: If Demand A = 10 and Demand B = 100 with only 11 TAs, assign 1 to A and 10 to B (10% to both)?

The Code Implementation

y_vars = [] for k in range(1, need + 1): y = model.NewBoolVar(f"y_{code}_{k}") y_vars.append(y) # Diminishing marginal reward reward = W_SEAT + (W_PROPORTIONAL * (need - k)) // need obj.append(reward * y) model.Add(sum(y_vars) == total)

The Mathematical Mechanism

The marginal reward for filling the $k$-th seat of course $c$ is:

R(c, k) = W_{\text{SEAT}} + \left\lfloor W_{\text{PROP}} \cdot \frac{\text{need}_c - k}{\text{need}_c} \right\rfloor

• For Course A ($\text{need}=10$), 1st seat gives reward $1,000 + 9,000 = \mathbf{10,000}$.
• 2nd seat of Course A gives only $1,000 + 8,000 = \mathbf{9,000}$.
• But the 1st through 10th seats of Course B ($\text{need}=100$) give rewards from $\mathbf{10,900}$ down to $\mathbf{10,000}$!
• The solver is mathematically forced to allocate proportionally across both!

Robustness

Supervisor Resolution & Fuzzy Name Matching

Source PDFs and CSVs spell faculty names inconsistently. `ta_solver.py` uses Levenshtein distance tokenization.

The Real World Discrepancy Problem

Faculty names vary across institute files:

  • Catalog: "Prof. Souradyuti Poul" vs Details: "Dr. Souradyuti Paul"
  • Catalog: "Dr. I Vinod Kumar Reddy" vs Details: "Dr. Vinod Reddy"
  • Catalog: "Prof. Santosh and Dr. Dhiman" (single token)

The same_person() Algorithm

def same_person(a, b): ta, tb = tokenize(a), tokenize(b) if len(ta) == 1 or len(tb) == 1: return bool(set(ta) & set(tb)) if levenshtein(ta[-1], tb[-1]) > 1: # Surname check return False return bool(set(ta[:-1]) & set(tb[:-1])) # Given name

Strips titles (Dr., Prof.), verifies surname similarity $\le 1$ edit distance, and intersects given names.
